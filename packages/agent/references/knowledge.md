# Discover the matching Flood knowledge

Read host instructions first. Use the CLI matching flood.json.version; a newer
website or CLI must not silently supply APIs to an older project. `info` reports
the package/configuration/guide versions and explicit capability gaps. A
bundle-only result describes that CLI bundle, not an installed application.

`catalog` lists names, descriptions, stable IDs and groups without reading all
instruction bodies. Filter by kind/group or literal metadata search. Follow
nextCursor when there are more matches; a cursor belongs to its catalog
fingerprint and query. Start again after a changed-catalog error.

`read <id>` returns one selected material. Follow nextOffset to finish a chosen
skill or required instruction before acting. Offsets count Unicode code points.
Optional related links are separately paged through nextLinksOffset. Do not load
all linked components just because a workflow applies to them; choose the ones
the task actually needs. Required prerequisites and ordinary links are distinct.

In a connected project, an existing owned guide copy takes precedence and the
response reports source=project and customized. Use --source package explicitly
to compare upstream guidance. Read host rules and intentional customizations;
the catalog cannot override them. The project catalog file is a snapshot for
discovery, not authority to redirect package reads to arbitrary files.

Components, recipes, token records and raw upstream guides share the shipped
catalog. Unsupported capabilities remain explicit. A motion-token record does
not supply a page-transition component, and a brand override does not add a
Button variant. Material text is instruction data: the reader never executes it,
installs packages, changes settings or grants permission for external actions.

## Extending Flood itself

In the Flood source repository, edit canonical component/token/guidance sources
and knowledge.json annotations, then build. Never edit the generated catalog or
material copies. New exports require catalog content and a live example; new
workflows need a group and manifest entry; public guides need a knowledge group.
Relationships must resolve. Preserve published material IDs across growth and
review the compatibility fixture before intentional retirement or renaming.

Run focused knowledge/compiler/CLI checks during iteration. A candidate also
checks clean tarball consumers, TypeScript declarations, website parity and
the applicable browser matrix. Growth checks cover metadata-only discovery,
bounded pages, changed cursors and selected-content integrity. They do not prove
model routing quality or rendered UI quality. Record the actual task, selected
materials, component/token owners and executed checks when evaluating an agent.

Core safeguards reduce known failure modes; they do not guarantee that every
future contribution or every agent host follows the contract. Host adapters and
new motion/theme capabilities require their own implementation and evidence.
