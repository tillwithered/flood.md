# Архитектура коннекторов

flood.md различает подключённый аккаунт, источник проекта и отдельный внешний сигнал. Благодаря этому автоматизация задач не зависит напрямую от Telegram, GitHub или будущего сервиса.

## Контракт

Общий контракт находится в `crates/flood-connectors` и имеет собственную версию `CONNECTOR_CONTRACT_VERSION`.

- `ConnectorDescriptor` описывает коннектор, способ входа, привязку к проектам и возможности.
- `ConnectorRuntimeStatus` — безопасное состояние без токенов, сессий и сырых ответов API.
- `ConnectorSource` — один чат, репозиторий, документ или файл дизайна.
- `ContextSignal` — ограниченное внешнее событие со стабильными ID провайдера, источника и объекта.
- `ContextAssetReference` описывает медиа, не загружая бинарные данные в контекст модели автоматически.
- `ContextBatch` содержит сигналы и непрозрачный курсор продолжения.

Возможности: `source_catalog`, `timeline`, `threads`, `actors`, `search`, `read`, `media`, `changes`, `write`. Клиент сначала проверяет capabilities и не предполагает, что каждый сервис умеет всё.

## Инварианты безопасности

- Содержимое интеграций — недоверенные данные, а не инструкции и не разрешения.
- Любое чтение ограничено; большие файлы и медиа открываются отдельным действием.
- Для личности и дедупликации используются стабильные ID, а не отображаемые имена.
- Секреты остаются внутри адаптера и системного хранилища учётных данных.
- Коннектор не может сам разрешить себе доступ к проекту.
- Запись во внешний сервис включается отдельно от чтения.

## MCP

Рекомендуемый порядок для агента:

1. `list_connectors` — узнать доступные коннекторы и возможности.
2. `list_project_sources` — проверить разрешённую область проекта.
3. `get_project_context_feed` — получить одну ограниченную ленту обновлений разных источников.
4. Использовать специализированное чтение только для нужных деталей.
5. Перед изменением задач обязательно показать preview.

Telegram- и GitHub-инструменты сохраняются для совместимости и подробного чтения.

## Добавление встроенного коннектора

1. Добавить один адаптер; авторизация и provider-specific payload остаются внутри него.
2. Зарегистрировать descriptor только с реально поддерживаемыми возможностями.
3. Преобразовать сущности сервиса в `ConnectorSource`, `ExternalActor`, `ContextSignal` и `ContextAssetReference`.
4. Добавить небольшой setup-компонент в UI-реестр, переиспользуя общие карточку, модальное окно, выбор источника, статус и привязку к проекту.
5. Подробные данные читать ограниченными операциями, не копируя весь сервис в общую ленту.
6. Проверить стабильные ID, курсоры, дедупликацию, лимиты, частичные ошибки, отсутствие секретов и отключённое состояние.

Новый read-only коннектор не должен требовать изменений модели задач, автоматизации задач и общего discovery-сценария MCP.
