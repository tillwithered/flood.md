# Рабочая композиция — current baseline refinement

[Индекс](README.md) · план сохранён 2026-09-19. **0.7.0 rejected. Новый baseline — текущий production Flood, не greenfield shell.**

Atomic gate0.6.9 остаётся закрытым. Compound0.7.0 rejected; активный candidate — [0.7.1](workspace-refine-071.md), который сохраняет current AppShell/window bar/sidebar/task flow и применяет DS поверх существующей структуры.

## Будущий вертикальный срез

**W-01 · Оболочка и ориентация.** Текущий проект, глобальная навигация, локальные разделы и действия относятся к разным уровням. Сохраняем прямую геометрию shell. Один общий header не дублирует title/actions следующей панели. Sidebar не перечисляет все существующие свойства объекта. Изменяемая ширина влияет на композицию, не на размер всех шрифтов.

**W-02 · Обзор проекта и список–детали.** Проверить «Мой фокус», «Делегировано», «Требует решения» как представления существующих данных, не новые task statuses. Основной вес — у задач и решений, не KPI-карточек. На широкой области detail может оставлять список видимым; на узкой detail заменяет список с явным «Назад». Возврат сохраняет фильтр, выбор и прокрутку. Не делать постоянную правую колонку складом чата, свойств и логов.

**W-03 · Просмотр результата агента.** Следом на той же оболочке: объект работы → краткое резюме → изменения/результат → источники и проверка → принять / запросить правки / отклонить. Переписка и технические логи вторичны. Identity агента и run state разделены; «готово к проверке», «применено» и «задача завершена» не синонимы. Кнопки применения в будущем sample только симулируются и явно подписаны.

Не проектировать три отдельных несвязанных mockups. После возобновления этого направления — один связанный walkthrough на одном наборе данных; W-03 добавляется после проверки list/detail.

## Что потребуется в будущем превью

- Один проект с 15–20 реалистичными задачами, длинными названиями, источниками, одним активным run, готовым результатом и вопросом к человеку. Все данные синтетические.
- Обзор; выбранная задача с содержимым; возврат в прежний список. Light/dark и узкое окно — одинаковые данные и порядок.
- Сравнивать одну гипотезу за раз: сначала композицию списка и detail, затем представление результата. Не менять одновременно palette, плотность, текст и навигацию.
- Отдельные статичные PNG с реально открытыми состояниями, а не только screenshot стартового экрана лаборатории. Телефонный review не равен объявлению нативной мобильной версии продукта.
- Сохранение состояния при переходах, длинное содержимое, 0/1/много объектов, keyboard/focus, ошибки и возврат. Рендеринг в браузере и реальный Tauri acceptance остаются отдельными проверками.

## Границы

Календарь, вложения, tree view и дополнительные density preferences требуют собственных контрактов по сценарию. Полноценный редактор с autosave/undo/conflict — отдельный пакет. Не расширять component API десятками флагов заранее.

Перенос GitHub picker в Svelte — отдельная implementation-задача: existing typed adapter, реальные permissions и Tauri. Не смешивать её с глобальным редизайном App.svelte и не считать продолжением работы над примитивами без запроса.
