# Композиция экранов

[Индекс](README.md) · читать перед выбором layout, а не после стилизации.

## Сборка от задачи

Сформулировать: «На этом экране человек [действие] над [объектом], чтобы [результат]». Затем обозначить основной content, навигацию, вторичные метаданные и точку решения. Если все четыре одинаково заметны, иерархия не построена.

У каждого экрана один устойчивый reading order: контекст → объект/заголовок → работа → относящиеся к ней действия. Одинаковые операции располагаются одинаково на соседних экранах. Общие actions относятся к странице, row actions — к конкретной строке. Не дублировать одну кнопку в трёх местах для видимости.

В качестве датированного свидетельства: [Linear, 12 марта 2026](https://linear.app/now/behind-the-latest-design-refresh) описывает снижение конкуренции навигации с содержимым и приведение header actions к предсказуемым местам. В Flood заимствуется задача иерархии, не их palette, размеры или иконки.

## AppShell

Постоянны: window chrome, primary navigation, место текущего проекта. Меняются: toolbar конкретной области и её content. Sidebar не размножает все настройки проекта в глобальную навигацию. Локальные tabs живут внутри проекта, не образуют второй глобальный sidebar.

Сохранять прямую геометрию shell и существующее управление collapse. Не заменять desktop application shell мобильным bottom navigation или web landing header. Прокручиваемая область имеет явного владельца; header не движется случайно вместе с editor.

На широкой поверхности возможны nav + index + detail. На узкой: nav сворачивается, затем index уступает место detail с Back. Не оставлять одновременно три независимых горизонтальных scrollbar. При возврате сохраняются query, filter, selection и позиция списка.

## Обзор проекта

Главный вопрос: что требует участия человека, что у него в работе и что делегировано. «Мой фокус», «Делегировано», «Требует решения» — представления существующих данных, не новые значения task status.

Анатомия: project title и короткий контекст → релевантное главное действие → рабочие группы → вторичная история. Не начинать с четырёх одинаковых KPI cards. Count полезен в заголовке группы, не обязан быть огромным числом в отдельной карточке.

Task row: название, только полезное состояние/срок/источник, исполнитель там, где он различает объекты. Требующий решения результат открывается в review, а не в абстрактный chat. Завершённое не конкурирует с текущей работой. Проверять экран с 15 задачами и несколькими длинными названиями, а не только с тремя идеальными строками.

## Task editor

Главный объект — сама задача и её содержание. Заголовок, статус и основные действия находятся над editor; редкие metadata не превращаются в большую форму перед текстом. Source/context доступны рядом или отдельной detail surface, но не вытесняют работу.

Порядок: название → описание/редактор → зависимости и связанный контекст → agent result/история по необходимости. Состояние сохранения остаётся у editor. При конфликте версия и local draft не теряются. Название и описание не ограничиваются одной строкой ради ровной карточки.

Просмотр результата и изменение задачи — разные намерения. «Принять результат» не является синонимом «Завершить задачу». Большой diff получает достаточно ширины; не помещать его в sidebar 300 px.

## Контекст проекта

Documents, Rules, Skills и Memory различаются назначением, а не только иконкой. Индекс показывает title, короткое summary, version и agent-access signal. Не повторять «Правило проекта» в каждой строке раздела «Правила».

Документ, rule или skill открываются как самостоятельный artifact editor: title/type, body, metadata/revisions, agent access, Save/Cancel. Не вставлять полноэкранный editor между двумя строками списка. Для продолжительной самостоятельной работы возможен route/page; modal подходит для ограниченного редактирования из индекса.

Agent access — отдельное разрешение с ясным scope, не декоративный eye icon. Версия и история не спрятаны за tooltip. Memory сообщает происхождение и superseded state, а не выглядит бесспорным системным фактом.

## Settings

Ограниченная ширина чтения, секции по намерению: appearance, данные, интеграции, MCP. Label и value/action в одном reading row. Helper text объясняет только нетривиальное последствие. Отсутствие helper у очевидного поля допустимо, отсутствие accessible label — нет.

Immediate controls и форма с Save не смешиваются без явного разделения. Опасные data actions вынесены из обычного потока. Внутри секции нет карточки вокруг каждой setting. На narrow layout label переходит над control; шрифт не уменьшается.

## Интеграции: три уровня

1. **Аккаунт:** вошёл ли пользователь, действительна ли сессия, какие действия поддержаны.
2. **Источник проекта:** какой repository/chat связан с конкретным проектом.
3. **Полномочия агента/автоматизации:** что можно читать или изменять в этом scope.

Один зелёный «Подключено» не доказывает все три. Settings интеграций управляют аккаунтом; проект показывает свои источники и действия над ними. Каталог использует общую анатомию и реальные logos, но не притворяется, что GitHub и Telegram авторизуются одинаково.

Подключение конкретного repository описано в [отдельном рецепте](github-repository-picker.md). Telegram connection не копирует GitHub permissions copy: показать собственный источник, режим и последствия.

## Review результата агента

Главное — предлагаемый результат и решение человека. Header содержит объект, автора/агента, provider и state. Затем summary/diff, источники, ограничения/проверки. Conversation и raw logs вторичны, доступны по запросу. Apply/Reject/Ask for changes размещаются у результата, не в несвязанном toolbar.

Связанные проверки, источники и история не создают три вложенные cards. Отличать факт, предположение и неизвестное. Подробности — [human–agent contract](human-agent.md).

## Поиск и bulk actions

Поиск находится у коллекции, которую ограничивает; глобальный поиск явно называется глобальным. Filter summary остаётся видимым. Selection не исчезает при скрытии строки фильтром; есть число выбранных и clear. Batch action показывает scope и последствия перед опасной операцией. Не применять action к невидимым результатам без явного «Все N» и подтверждения scope.

## Проверка композиции до polish

Убрать brand и тени мысленно: остаются ли понятны объект, иерархия и действие? Проверить empty, sparse и dense варианты; long RU; отсутствие avatar; narrow content. Если объясняющий абзац нужен, чтобы понять куда нажать, сначала пересмотреть структуру. Не компенсировать лишнюю колонку меньшей типографикой.
