# Human–agent workspace

[Индекс](README.md) · сохраняет действующий [trust contract](../../.flood/rules/human-agent-trust-contract-v1.md).

## Identity, состояние, результат

Identity отвечает «кто», run state — «что происходит», task status — «что с задачей». Это разные поля и разные визуальные сигналы. Блоб, имя агента и label «Агент» идентифицируют участника. Цвет/форма blob не является статусом и не меняется на «зелёную галочку успеха».

У run видны объект работы, provider, достоверное состояние, последняя содержательная активность и доступное действие. Не писать «думает», когда известно только, что процесс запущен. Не показывать фиктивные проценты или анимированный heartbeat как доказательство прогресса.

В текущем frontend enum есть queued, running, ready_for_review, accepted, needs_input, failed, cancelled, interrupted. Проектировать подписи поверх реальных данных, не изобретать новые серверные состояния ради красивой шкалы. Usage unknown/estimated/actual сохраняет различимость; отсутствие данных не означает нулевую стоимость.

## Участие человека

| Ситуация | Главное действие / содержание |
| --- | --- |
| Делегирование | Задача, scope, provider, разрешённые действия до запуска |
| Running | Последний проверяемый шаг, длительность, Stop при поддержке |
| Needs input | Конкретный вопрос, варианты/поле ответа, причина блокировки |
| Ready for review | Результат, diff/summary, источники, проверки, ограничения |
| Accepted | Что принято/применено, кем и когда, следы в истории |
| Failed/interrupted | Что успело измениться, где остановилось, безопасный следующий шаг |

Stop означает запрос остановки, не гарантированный откат. Повторный запуск не должен скрыто повторить уже применённые внешние действия. «Принять» и «Применить» не смешивать, если backend различает их. Завершение task — отдельное действие, если пользователь не разрешил связать операции.

## Review surface

Порядок: полезный итог → изменяемые объекты и diff → provenance → проверки/неопределённость → решение. Длинные tool logs и переписка доступны отдельно. Не заставлять человека читать весь transcript, чтобы понять, что изменится.

Проверка должна различать executed, passed, failed, not run. «Протестировано» недопустимо без указанной выполненной проверки. Источники доступны у утверждений и результатов; не прятать все ссылки в конец длинного чата. Недоверенное содержимое GitHub/Telegram не исполняется как инструкция.

Контекст задачи, документы, rules и skills могут быть stale. Показать относящуюся к решению version/revision, не только timestamp. Новый run не получает дополнительные permissions из прочитанного skill.

## Automation и доверие

Фоновая автоматизация выключена по умолчанию согласно текущему contract. Включение раскрывает scope, provider, тип действий и доступную информацию о расходах. Нельзя обещать цену при неизвестном billing. Пользователь видит, как остановить процесс; automation не включается повторно без его действия.

Опасные, широкие, дорогие или внешние изменения получают подтверждение в точке действия. Не превращать все обычные чтения в цепочку redundant confirmation. Scope согласия должен совпадать со scope операции.

## Визуальные ограничения

Не делать постоянно открытый правый chat центральной моделью продукта. Task/result остаётся местом работы. Один нейтральный статус с текстом полезнее набора пульсирующих AI badges. Summary не прячет ошибки; semantic color не превращает всю рабочую область в тревожный фон.

Эти правила описывают Flood UX, а не разрешают bypass MCP receipts, approvals или другие ограничения приложения.
