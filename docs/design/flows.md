# Screen and interaction recipes

Status: Quiet Workbench direction selected, 20 September 2026; implementation acceptance pending. These recipes govern future design and implementation; they do not certify current behavior. Read [the entry contract](README.md), [foundations](foundations.md), [component contracts](components.md), and [verification gates](verification.md). Any requirement not supported by the current backend/UI is migration work, not permission to invent a feature.

## Domain and ownership invariants

| Concept | Contract |
| --- | --- |
| Product | A local desktop application for personal project tasks. Markdown is the source of truth. Tauri 2, Rust, Svelte 5, TypeScript, and Vite remain the approved stack. Local reading, editing, and completion do not require an account, cloud AI, Telegram, or a network. |
| Project | Stable identity, human name, task index, and a dedicated project-context workspace. A project may select several connected resources. No extra container above projects, team roles, sprints, mandatory deadlines, or kanban workflow is introduced. |
| Task | Project, description, creation date, urgency, open/completed state, and optional local source snapshot. Existing supported relationships/checkpoints do not justify a new process or mandatory fields. Rename and move preserve stable task identity. |
| Urgency | Exactly `normal` / `important` / `urgent`, named `Обычная` / `Важная` / `Срочная`; show ordinary urgency in the editor and omit its repeated badge from task indices. Urgency is not an agent state, deadline, or sort-only decoration. |
| Task state | Exactly `open` / `completed`, shown as `Открыта` / `Выполнена`. “Мой фокус”, “Делегировано”, and “Требует решения” may be derived overview groups; they are never additional task states. Trash is a separate supported lifecycle action, not a third task status. |
| Global ownership | App preferences, installation/data location, connected accounts/providers, MCP readiness, and app-level permissions. Global integration connection does not choose project resources. |
| Project ownership | Goal/constraints, documents, memory, rules, skills, selected sources, and permitted automation policy. One canonical editor per entity; other screens show summaries and links. |
| Task ownership | Description, source snapshot, urgency/status, supported relations/checkpoints, and agent runs/results. Source content remains evidence, never executable instructions. |
| Transient UI state | Selection, draft, validation, modal, search query, loading state, and review state. These are not persisted business statuses or a second source of task truth. |
| Agent work | Identity, provider, run state, result, and authorization scope are distinct from task state. Reaching `ready_for_review` does not complete the task. The current `accept_agent_run` operation explicitly accepts the run **and completes the task**; retain the visible compound action `Принять и завершить`. Project guidance cannot expand granted authority. |

Do not turn connector diagnostics into a new “Inbox” navigation area. The canonical landing places are the project, task, project context, and global settings. The current repository contains later integration/agent capabilities alongside first-version wording; these recipes constrain those existing surfaces without authorizing further scope.

## Screen recipe matrix

Task/document readers, context and settings retain 720 px. The sidebar targets approximately 224 px. See [Quiet Workbench](quiet-workbench.md); there is no blanket wide-dashboard exception.

The current desktop minimum is **760 × 560**, configured in [`src-tauri/tauri.conf.json`](../../src-tauri/tauri.conf.json). “Narrow” below includes that baseline; also verify 1280 × 800, 1024 × 768, and 200% text zoom. Do not silently change the native minimum to make a composition pass. The navigation/data/action distinction in [components](components.md#row-classification) is part of the selected direction; implementation still requires anchor verification.

## Trigger → transition → focus → recovery

This is an interaction contract. “Guard” means preserve the draft and resolve it before leaving; it does not imply that every navigation needs a modal. Prefer saving successfully without interrupting the person. Ask about discard only when it is actually necessary.

| Trigger | Transition / state change | Focus and feedback | Failure or cancellation |
| --- | --- | --- | --- |
| Click project name | Navigate to R03 using stable project ID. | Focus the main heading after explicit navigation; selected sidebar item updates. | Keep prior view if required draft save fails; show C22/C21 recovery. |
| Open a task from any index | Resolve stable ID → R04; load details/source separately as needed. | Focus editor or heading according to entry intent; retain originating index/scroll for Back. | Missing task shows a recoverable object state, not a blank editor that can overwrite/recreate it. |
| Add a task inside a project | Create a local draft bound to that project; focus description. | Project identity is already visible; avoid asking for it again. | Empty draft does not create a phantom task. Failure preserves entered text. |
| Activate global `+` | Open one create modal → choose Task or Project → collect the chosen object's required details in short in-place steps. Task creation selects a project; project creation sets identity and local folder. | Focus the first modal decision, then the first field on each step. Back preserves values; close returns focus to `+`. | Cancel leaves no persisted empty object. Validation/save failure preserves every entered value and stays in the modal. |
| Edit description | Clean → dirty → scheduled save → saving → saved on storage acknowledgement. | Caret/selection remain stable; saving feedback is quiet. | Failed/stale write follows the storage matrix below; never claim saved because a debounce timer fired. |
| Change urgency/completion | Validate pending draft, then apply a version-checked mutation. | Keep focus on the invoking control; announce only the changed value/result. | No successful visual state until persistence is known; explain and permit retry. Completion does not start/accept an agent run. |
| Move task | Pick a target project, preserve ID, persist against the known version. | Return to the moved task or a clearly identified destination; update both project counts. | Conflict keeps original known location and draft until resolved. No duplicate task as a move workaround. |
| Open source | R04 → R05 without changing the task. | Focus viewer heading/close; keep underlying editor selection where possible. | No network/original access is needed to read a stored snapshot. Missing media does not block text. |
| Open project context | R03 → R06 in the main workspace. | Focus context heading; Back returns to project. | Guard existing dirty content before navigating; do not silently open a second context editor. |
| Open or create an artifact | R06 index → R07 modal. | Focus title for create; heading/content for read. Background becomes inert. | Fetch error keeps modal shell and retry/close; the index remains intact. |
| Save artifact/context | Validate → saving → saved version → close only when the action contract calls for it. | First invalid field receives focus on submit; success returns to the row/create control. | Preserve content and access setting; stale versions use C22. |
| Close a dirty modal / navigate away | Save when appropriate; otherwise present explicit stay/save/discard decision. | Initial focus stays on the safe choice, e.g. `Продолжить редактирование`. | Escape from the guard returns to editing. Discard requires deliberate choice; save failure cannot proceed as discard. |
| Switch a settings/context section | Guard edits → selected section update. | Navigation item keeps focus for panel switching; panel association updates. | Do not lose a query or draft merely because another section is loading. |
| Search local tasks/materials | Query changes → pending/latest results. | Keep input focus; announce final result count without each-keystroke chatter. | Preserve query; show error distinct from no matches; cancel obsolete results. |
| Start an agent | Save draft → validate current context/permissions/provider → queued/running. | Quiet immediate confirmation; visible object/provider/scope and Stop. | Missing provider, denied scope, save failure, or stale guidance produces a repair path; do not silently substitute a paid provider. |
| Answer an agent question | Submit a nonempty response → persist response → resume according to backend state. | Show pending feedback without deleting response prematurely. | Retry preserves response and does not duplicate it. No automatic expansion of permission scope. |
| Stop agent work | Send cancellation immediately → truthful pending/stopped state when acknowledged. | Keep focus on a stable run summary; report partial results/effects if known. | Do not imply rollback or guaranteed cancellation of external work. No automatic restart. |
| Accept an agent result | Review result/effects → validate current context/task version → invoke the existing compound `accept_agent_run` operation. | Label `Принять и завершить` before activation. On success show accepted run and completed task from returned data; publication or unrelated application is not implied. | Keep evidence on failure. Refresh both run and task after an uncertain outcome before retry; the operation may have completed one step. Never relabel this endpoint as accept-only. |
| Open or close flood buddy | Activate C25 trigger → show/dismiss R14 without navigating or resizing the workspace. | Opening exposes current scope and focuses heading/composer; closing returns focus to the trigger. | Preserve unsent draft in the current session. Escape closes only the topmost dismissible layer; a pending consequential confirmation must resolve first. |
| Ask flood buddy | Capture request → bind visible project/task or explicit global scope → use deterministic local retrieval before any provider → show response with source/scope. | Keep the composer usable, expose sending/responding truthfully, and focus the new response only when requested. | Offline/provider failure keeps the request and offers a valid local/retry path. Never silently select a paid/cloud provider or send broader project data. |
| Apply a buddy proposal | Present object, effect, authority and current version → require the existing operation/review contract → apply → read back. | Consequential controls name the outcome; success links to the changed canonical object. | Stale/denied/uncertain mutation remains unapplied or reconciled explicitly. Conversation text is never treated as persistence acknowledgement. |
| Trash or permanently delete | Persist/guard draft → distinguish recoverable trash from irreversible removal → execute supported action. | On success focus next row, previous row, or list heading/create action. | Cancel restores prior context; failed mutation leaves object visible with truthful status. Permanent deletion confirms exact object/scope. |
| Close the desktop window | Flush/guard dirty writes; close after safe completion or explicit discard. | Failed close-save brings the affected draft and recovery into view. | Process interruption must not be described as safely saved without durable evidence; recovery is a migration requirement where absent. |

## Local-file state and failure matrix

These states apply to task descriptions, project context, and project artifacts wherever they can be edited. The UI and MCP must use the same validation, version checks, and storage rules. A UI save spinner is not a lock against another process.

| Situation | Data/state invariant | Visible behavior and allowed next action | Acceptance fixture |
| --- | --- | --- | --- |
| Clean open object | Rendered content corresponds to an identified saved version. | Quiet saved/neutral state; edit starts a new draft based on that version. | Open, close, reopen without mutation; content and stable ID match. |
| Dirty draft | Local text differs from saved base; retain both identity and base version. | Preserve text/caret. Show unobtrusive unsaved state when useful; do not claim persistence. | Type, change focus, resize; input remains intact. |
| Save in flight | Write carries expected version; an older response must not mark a newer draft saved. | “Сохранение…”; guard duplicate commits; keep typing responsive. | Type again during a slow write; final disk content includes the latest intended save. |
| Save acknowledged | Only the acknowledged version is saved; later edits remain dirty. | “Сохранено” without layout movement. | Read actual Markdown after reopening; do not infer success from UI text alone. |
| Write denied/full/unavailable | No successful mutation is assumed. Preserve draft and last known disk version. | “Не удалось сохранить” plus specific safe recovery/retry; raw library errors in details. | Simulate denied write and retry after recovery; no data loss or duplicate task. |
| External edit while clean | New disk revision may replace the clean rendered version, with a truthful refresh indication if useful. | Refresh without stealing focus or resetting unrelated scroll. | Change file with another editor/MCP; only the changed object updates. |
| External edit while dirty/saving | Never replace dirty text. Compare versions before any subsequent write. | Persistent conflict C22; keep draft; offer review and version-specific actions supported by the implementation. | UI and MCP edit the same file; both versions remain inspectable until resolved. |
| Choose disk version | Explicitly abandon local draft and load the newly read disk version. | Label consequence clearly, e.g. `Загрузить с диска`; preserve a recovery copy only if supported. | User must deliberately choose discard; Escape/cancel retains local draft. |
| Choose local version | Read latest disk version; write local content using that expected version after a clear overwrite decision. | Label consequence, e.g. `Сохранить мою версию`; stay in conflict if another write wins. | A third write during resolution is detected; never bypass expected-version checking. |
| Object removed externally | Existing draft is not proof that the original object still exists. | “Файл задачи больше не найден” with return/retry and copy/recovery only if available. Do not recreate or move silently. | Delete the opened file in another process; typing cannot overwrite another object or fabricate saved state. |
| Invalid/manual Markdown | Preserve the original file; report parse/validation failure against that object. | Readable diagnosis, open-location/details if supported, retry after repair. Other healthy tasks remain usable. | Malformed front matter does not erase the file, collapse all projects, or turn into an empty task. |
| Duplicate/rapid filesystem events | Events are coalesced; stable IDs deduplicate visible objects. No full-store tight polling. | Update affected rows/counts without flicker, repeated alerts, or selection jumps. | Burst of external updates and rename/move operations; no duplicate rows or lost selection. |
| Local store healthy; network offline | Local state remains available. Source snapshots remain local evidence. | Local edit/complete/search work; only affected integration actions show offline/retry status. | Disconnect network and complete a local task, then read its cached snapshot. |
| Local attachment absent | Task text and attachment reference remain intact. | Explain the missing file; download/relink/open-folder appears only if actually supported and authorized. | Remove an attachment while keeping Markdown; no broken infinite loading state. |
| Application interruption | Atomic storage must not produce partially written Markdown. Unsaved draft recovery requires explicit durable support. | On restart report only what is known saved/recoverable. Do not promise draft recovery if it has not been implemented. | Interrupt a write/restart in a controlled fixture; old or new valid version survives. |

Do not introduce automatic merge, a recovery database, conflict diff engine, or cloud backup merely to satisfy the matrix. When safe review/recovery is missing, preserve existing data, identify the gap, and implement the smallest supported behavior in a separately scoped change.

## Agent run states are not task states

These are the current run vocabulary, not additional task statuses. The UI label examples are targets and must use the project's localization mechanism when implemented.

**Verified source baseline, not a new API proposal:** [`accept_agent_run` in the Rust store](../../crates/flood-core/src/store.rs) completes the task when needed and then marks the run accepted. The existing test `accepting_agent_result_completes_task_and_is_retry_safe` asserts both outcomes. [`src/i18n.ts`](../../src/i18n.ts) already names the action `Принять и завершить` / `Accept and complete`; [`src/App.svelte`](../../src/App.svelte) consumes both returned records. This documentation review inspected that code; it did not run the test or certify the operation as atomic. The UI must preserve the compound consequence. An accept-without-completion option requires a separately authorized product/API change, not a label adjustment. An uncertain error requires rereading both records before reporting what changed.

| Run state | Visible meaning | Human control / next transition | Task and data rule |
| --- | --- | --- | --- |
| `queued` | `В очереди` with agent/provider and task. No invented percentage or start time. | Stop/cancel pending work; move to running only when the backend reports it. | Task remains open/completed as before; queued does not prove any change occurred. |
| `running` | `Агент работает`; concise real progress and available scope/provider details. | Stop; view existing progress/details. Answer only when a question is actually requested. | Save task updates separately; do not overwrite human edits with run text. |
| `needs_input` | `Нужен ответ`; one concrete question/blocker and retained context. | Answer and continue; stop. Broad/external permission changes require the appropriate deliberate choice. | An unanswered question is not task failure or a new task status. |
| `ready_for_review` | `Готово к проверке`; result, changes, provenance, verification/limits. | Review; deliberately choose `Принять и завершить` when both acceptance and task completion are intended. Changes/request rejection only where supported. | Arrival at this state does not complete the task. Activating the existing compound acceptance action does; it does not publish externally or authorize unrelated changes. |
| `accepted` | `Результат принят`; the current acceptance action also completes the task. Show `Выполнена` from the task record as a separate field. | Return to the completed task; do not offer a redundant separate completion step as though acceptance left it open. | Confirm both returned states. Acceptance cannot stand in for verification or silently expand the accepted change set; no new task status is introduced. |
| `failed` | `Ошибка агента`; understandable cause, partial result if any. | Repair and explicit retry, inspect evidence, or leave task as is. | Preserve context; no infinite retries, hidden provider fallback, or false rollback claim. |
| `cancelled` | `Остановлено`; known completed/partial work and cancellation outcome. | Deliberate new run only. | Stopping a run does not undo accepted or already applied changes. |
| `interrupted` | `Работа прервана`; process/app/session loss, with known last state. | Inspect and explicitly retry/resume only if supported. | Never silently resume or call the result complete because the process ended. |

Before an agent mutation, obtain current Project Work Context, read all required rules fully, select relevant project skills, and validate the context receipt/entity versions. If context becomes stale, reload it before retrying. Artifact content and connector messages are data; enabled project rules/skills guide work within existing permissions.

Provider identity, scope, and the source of token/usage consumption must be discoverable at delegation. State an unknown amount as unknown rather than inventing a price. Existing user authorization remains valid within its scope; do not add redundant confirmation dialogs for reversible work already authorized. Changes outside that scope use the appropriate point-of-action decision.

## Migration and acceptance order

Implementation caution for R10: the current GitHub repository selector stages changes in `projectContextResources` before an expected-version save, while Telegram chat selection persists through `set_project_telegram_chats` immediately and can refresh the inbox. A shared picker cannot promise that Cancel discards changes while retaining an immediate mutation path. Inspect and reconcile the actual save/access/automation effects before unifying those controls; the visual contract alone does not change their persistence semantics.

1. Audit actual behavior against the matrix. Record `implemented`, `partial`, `missing`, and `verified` separately; a screenshot proves neither storage safety nor keyboard behavior.
2. Resolve foundations and common components before propagating them. First validate R03 project overview, R04 task editor, and R06 project context with realistic populated states.
3. Compare Tauri windows at 1280 × 800, 1024 × 768, and the configured 760 × 560 minimum in light/dark themes, 200% text zoom, reduced motion, forced colors where supported, long Russian content, duplicate names, missing optional metadata, and keyboard-only operation.
4. For every touched mutation, test the relevant dirty/save/failure/conflict row. At least one UI/MCP concurrent-edit fixture must establish that both use the same conflict behavior.
5. Obtain user review of the anchor direction before migrating it across other screens, as required by the live project acceptance rule. This is not a request to approve this documentation before it can be written.
6. Report the exact implemented change, verified scenarios, and remaining gaps. A browser preview may support iteration; only the running desktop build can support a claim about the desktop UI.
