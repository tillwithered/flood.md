# MCP в flood.md

Вместе с Windows-установщиком flood.md поставляется локальный stdio MCP-сервер. Совместимый AI-клиент получает управляемый доступ к тем же Markdown-проектам и задачам, с которыми работает desktop-приложение.

English version: [mcp.md](mcp.md).

## Поддерживаемые клиенты

Локальный сервер работает в клиентах, которые умеют запускать команду на компьютере пользователя: Codex, Claude Desktop, Cursor и других. Откройте **Настройки → MCP и AI**, выберите клиент, скопируйте готовую конфигурацию, затем перезапустите клиент или откройте новую сессию.

Обычный облачный чат ChatGPT не может запустить <code>flood-mcp.exe</code>. Для remote MCP OpenAI требуется HTTPS endpoint. Облачный мост намеренно не входит в локальную версию flood.md.

## Рекомендуемый сценарий

При инициализации сервер передаёт агенту короткие правила работы и публикует четыре готовых MCP-промпта: <code>review-project-state</code>, <code>review-project-updates</code>, <code>review-telegram-project</code> и <code>work-on-flood-task</code>. Совместимый клиент может показать их как готовые сценарии, поэтому модели не приходится угадывать правильную последовательность по длинному списку инструментов. Чтение и изменения при этом остаются отдельными ограниченными инструментами.

Запросы агента на синхронизацию Telegram и подготовку изображений обрабатывает desktop-процесс flood.md. Достаточно, чтобы приложение было запущено и Telegram был подключён: держать открытым экран интеграции не требуется.

Коннекторы обнаруживаются по возможностям. <code>list_connectors</code> показывает установленные сервисы, <code>list_project_sources</code> — разрешённую область проекта, а <code>get_project_context_feed</code> возвращает одну ограниченную ленту сигналов Telegram и GitHub. Подробности читаются специализированными инструментами. См. [архитектуру коннекторов](connectors.ru.md).

Новые сигналы коннекторов сохраняются в общей ограниченной очереди. <code>list_automation_events</code> по умолчанию показывает необработанные события без полной переписки и медиа: модель сначала выбирает нужную ссылку, а подробный контекст запрашивает отдельно. <code>claim_automation_events</code> атомарно объединяет близкие события одного проекта и источника в небольшой пакет, а <code>resolve_automation_event</code> фиксирует проверенный итог. Если не хватает одного конкретного уточнения, событие хранит вопрос; <code>answer_automation_event</code> принимает только прямой ответ пользователя и безопасно возвращает то же событие в очередь. Повторная синхронизация того же сообщения не создаёт второе событие; прерванная обработка восстанавливается, временная ошибка повторяется с паузой не более трёх раз, а создание или пропуск Telegram-задачи переводит исходное событие в обработанное состояние.

<code>get_telegram_sync_status</code> также возвращает безопасное состояние коннектора и конкретное следующее действие. Пароли, API-ключи и Telegram-сессия в общий MCP-каталог не записываются.

### Фоновый разбор без обслуживания

По умолчанию flood.md синхронизирует и группирует входящие локально, но не передаёт их модели. В **Настройки → MCP и AI** можно выбрать установленный Codex, Claude Code или Gemini CLI либо оставить автоматический выбор. Один явный переключатель фоновой обработки разрешает desktop-приложению отправлять выбранному локальному агенту небольшие пакеты, создавать только ясные задачи, связывать дубли и пропускать шум. События накапливаются до 45 секунд и обрабатываются пачкой до 12 записей, поэтому новое сообщение не запускает отдельный модельный запрос. Вместе с режимом включается автозапуск Windows; закрытие окна прячет flood.md в системный трей, а явное действие «Завершить работу» в меню трея полностью останавливает процесс. Для обычного разбора отдельно настраивать каждый проект не нужно: область уже задают привязанные Telegram-чаты и их режим входящих.

На один запуск передаётся только выбранный пакет, ограниченный контекст проекта, краткий список открытых задач для проверки дублей и, если выбранный CLI поддерживает этот путь, не больше четырёх относящихся к пакету изображений. Полная переписка не выгружается. Все сообщения и изображения помечаются как недоверенные данные. MCP работает независимо: совместимый клиент по-прежнему может управлять flood.md только по явному запросу пользователя и не включает фоновую обработку сам.

Необязательное разрешение **Контекст проекта → Автоматизация → Выполнять новые задачи** позволяет после разбора сразу поставить созданную задачу встроенному Codex runner. Оно выключено для каждого проекта по умолчанию, хранится вне `project.md` и требует доступную локальную папку или репозиторий с включённым доступом агента. Запуск может менять только эту рабочую папку; публикация, push и сообщения запрещены, а результат остаётся на проверке. Повторная обработка события не создаёт второй запуск. Отключение глобального фонового разбора сразу прекращает новые обращения к модели, не удаляя уже собранные локальные входящие.

### Разобрать Telegram проекта

1. Начать с <code>get_workspace_brief</code> или <code>get_project_triage_context</code>.
2. Проверить свежесть синхронизации Telegram.
3. Читать ограниченную ленту проекта, а не запрашивать всю историю чата.
4. При необходимости открыть соседние реплики выбранного сообщения или одно конкретное изображение.
5. Если поручению нужен технический контекст, поискать в разрешённом локальном или GitHub-репозитории.
6. Показать точный план задач и применить его, когда текущий запрос пользователя явно разрешает создание.
7. Подтвердить только реально обработанные сообщения. Это двигает локальную закладку flood.md, но не отправляет read-receipt в Telegram.

Если пользователь в том же запросе явно просит выполнить найденные задачи, передайте <code>run_with_agent=true</code> уже в <code>preview_project_telegram_tasks</code> и без изменений — в <code>apply_project_telegram_tasks</code>. Флаг входит в confirmation token: режим «только создать» нельзя незаметно повысить до запуска после preview. В очередь попадают только действительно новые задачи, а найденные дубли повторно не запускаются.

Пример:

> В проекте «zakup.io» проверь свежесть Telegram. Найди явные поручения от Димы, при необходимости открой соседние сообщения, скриншоты и разрешённые GitHub-репозитории. Создай задачи, расставь срочность и не дублируй существующие.

### Обязательный Project Work Context

Перед планированием или изменением конкретного проекта вызовите <code>get_project_brief</code>. Он возвращает канонический <code>work_packet</code>: описание проекта, актуальную память, разрешённые документы, rules, skills, источники и открытые задачи. Rules с включённым Agent access действуют как постоянные инструкции проекта; skills выбираются по назначению текущей работы. Ни один материал не расширяет разрешения и не отменяет preview, expected version или подтверждение пользователя.

`WorkPacket v3` использует единый бюджет текстового содержимого: 32 000 символов по умолчанию, с допустимым диапазоном 8 000–64 000 через `context_budget_chars`. Поле `budget` сообщает включённый текстовый объём, приблизительное число токенов всего сериализованного packet и каждую усечённую секцию вместе с инструментом точечного дочитывания. Полные дубли `project`, `task` и task digest больше не возвращаются по умолчанию; временный `include_legacy_snapshot=true` предназначен только для миграции старого клиента. Метаданные, версии, разрешения и `context_revision` не зависят от текстового бюджета.

Rules с доступом агента входят в `guidance` всегда. Для конкретной задачи Flood детерминированно выбирает до трёх project skills по совпадениям с названием, summary и содержимым задачи; `guidance` сохраняет точные ID, версии и причину выбора. Остальные skills возвращаются как `deferred_project_skills` без полного текста и читаются точечно через `get_project_workspace_item`. В проектном brief без конкретной задачи все skills остаются deferred.

Бриф также возвращает <code>context_revision</code> и сохраняет receipt в текущей MCP-сессии. Изменения проекта и задач без такого receipt отклоняются. Если обязательное rule не поместилось полностью, <code>budget.truncations</code> указывает <code>get_project_workspace_item</code>, а receipt блокирует изменения, пока агент не дочитает каждое указанное правило целиком. Если <code>project.md</code>, память, разрешённое правило или skill изменились другим процессом, receipt устаревает и сервер требует повторить <code>get_project_brief</code> или <code>get_task_work_context</code>. Изменение с проверкой версии, которое та же MCP-сессия реально записала, продвигает только известную версию проекта или конкретного материала; параллельные непрочитанные изменения и недочитанные rules остаются stale/incomplete. Read-only инструменты остаются доступными без receipt.

Между этапами работы вызывайте `check_project_context({project_id})`, чтобы проверить актуальность без повторной загрузки Markdown. Инструмент сравнивает версию проекта и доступных материалов с последним receipt этой MCP-сессии. Ответ содержит `status`, `context_revision`, `previous_context_revision`, `project_changed`, ID изменённых материалов со старой/новой версией и `pending_rule_ids`. Тексты и история не возвращаются. Удаление материала и отзыв Agent access одинаково обозначаются `removed`; ранее недоступные материалы не раскрываются. Изменения задач не входят в эту проверку: при записи задачи по-прежнему нужна её актуальная `version`.

Состояния: `missing` — receipt ещё нет; `stale` — контекст изменился; `incomplete` — обязательные rules не дочитаны; `current` — контекстный маршрут готов. `project_changed=null` означает отсутствие исходной версии для сравнения. При `missing`/`stale` нужен новый бриф проекта или задачи; при `incomplete` — точечное чтение правил. Проверка только наблюдает: повторные вызовы и просмотр списка не подтверждают изменения, не снимают отметку непрочитанных rules и не дают права записи. Новый MCP-процесс начинает без receipt.

### Работать с существующей задачей

Используйте <code>get_task_work_context</code> как точку входа. Он объединяет Markdown-задачу, ограниченный контекст проекта, компактную память прошлых запусков, разрешения источников и центрированное Telegram-обсуждение. Если сообщение уже вышло из скользящего кеша, flood.md возвращает снимок источника, сохранённый вместе с задачей. Память считается данными проекта, а не инструкцией или расширением полномочий агента.

Если `work_packet.budget.truncated=true`, агент не должен угадывать отсутствующее содержание: используйте `next_tool` соответствующей секции и дочитайте только нужный item. Увеличивать общий бюджет следует лишь когда точечного чтения недостаточно.

Ссылки на GitHub issue и pull request в задаче, сохранённом источнике, обсуждении или результате последней контрольной точки автоматически сопоставляются с разрешёнными GitHub-репозиториями проекта. Рабочий контекст возвращает до трёх безопасных ссылок и предлагает <code>get_task_github_context</code>, который читает точный объект, ограниченное описание и последние комментарии. Ссылки на репозитории без доступа агента игнорируются. Режим остаётся read-only и не обходит все подключённые репозитории.

Разрешённые локальные repository и directory также возвращаются как <code>local_git_resources</code>. Один вызов <code>get_task_local_git_context</code> показывает текущую ветку, HEAD, ограниченный список изменений, компактный staged/unstaged diff, а также недавние коммиты и строки `TODO`/`FIXME`, совпавшие со значимыми словами заголовка задачи. Для каждой предполагаемой связи Flood явно возвращает причину текстового совпадения и не сохраняет её как установленный факт. Flood запускает только фиксированные read-only команды Git без shell, не читает содержимое untracked-файлов и исключает diff похожих на секреты, служебных каталогов, символических ссылок, удалённых файлов и файлов больше 256 КБ.

Если текущий запрос пользователя явно просит выполнить задачу, <code>queue_task_for_agent</code> ставит её встроенному локальному Codex runner. Нужен хотя бы один доступный локальный источник типа repository или directory с включённым доступом агента. Открытый desktop подхватывает очередь автоматически; закрытый — при следующем запуске. Повтор того же <code>request_id</code> не создаёт второй запуск. Состояние и компактный итог доступны через <code>get_agent_run</code>. Если запуск задал конкретный вопрос, <code>answer_agent_run</code> сохраняет ответ и продолжает ту же сессию. Готовый результат можно принять отдельным <code>accept_agent_run</code>, который завершает задачу и безопасно обрабатывает повтор запроса.

После существенного прогресса, появления результата или реального блокера используйте <code>append_task_checkpoint</code>. Контрольная точка хранит короткий итог, фактические проверки, оставшуюся работу, блокер и ссылку на результат отдельно от исходной постановки. Для записи нужны свежая версия задачи и стабильный <code>request_id</code>; неопределённый повтор не создаёт дубль. Встроенный runner сохраняет такую контрольную точку сам после успешного структурированного ответа Codex. Полный transcript в задачу не записывается.

Встроенный runner использует сохранённую авторизацию Codex CLI, но для фонового запуска игнорирует общую пользовательскую конфигурацию Codex. Поэтому посторонние MCP-серверы, плагины, профили и переопределения модели не меняют задачу Flood и не расходуют её контекст незаметно. При этом продолжают действовать `AGENTS.md` самого репозитория, постановка Flood, изображения, sandbox рабочей папки и схема структурированного результата.

Если пользователь явно просит продолжить несколько задач проекта, <code>queue_project_for_agent</code> создаёт один ограниченный приоритетный пакет вместо отдельного вызова для каждой задачи. По умолчанию в него входит до пяти задач, максимум — двенадцать. Уже выполняемые и заблокированные задачи, ожидание ответа и готовые к проверке результаты пропускаются, а desktop исполняет пакет последовательно. Повтор того же <code>request_id</code> возвращает исходный пакет и не захватывает задачи, появившиеся позднее.

Для согласованного изменения реестра есть <code>apply_task_batch</code>: один вызов может создать, изменить и связать до 25 задач. Новые задачи получают локальные <code>operation_id</code>, поэтому подзадачи можно связать с родительской задачей до того, как агент узнает их постоянные ID. Для каждой существующей изменяемой задачи один раз передаётся актуальная версия. Flood сначала проверяет весь план, проекты, версии и циклы, затем записывает его целиком; ошибка проверки не оставляет половину изменений. Стабильный <code>request_id</code> безопасно возвращает результат исходного пакета, а локальный журнал завершает запись после аварийного перезапуска. Инструмент применяется только к уже одобренной пользователем группе изменений, а не вместо preview или согласования.

<code>get_project_overview</code> даёт ограниченный фактический обзор без превращения Flood в KPI-панель: доступная сейчас работа, блокировки, давно не менявшиеся открытые задачи, недавние постановки и завершения, а также запуски агента, где нужен человек. В текущем формате задачи нет отдельного времени завершения, поэтому раздел завершённого за период явно использует время последнего изменения и сообщает об этом ограничении. Промпт <code>review-project-state</code> превращает эти данные в короткий личный обзор, ничего не меняя.

Задачи можно связать через <code>link_tasks</code> как <code>related</code>, <code>subtask_of</code> или <code>blocked_by</code>. Связи направленные, действуют внутри одного проекта и сохраняются в Markdown; циклы подзадач и блокировок отклоняются. <code>get_task_readiness</code> показывает незавершённые блокеры, а <code>get_task_work_context</code> включает ту же вычисляемую готовность. После завершения всех блокирующих задач работа становится доступной автоматически — отдельный переключатель не нужен.

Весь цикл пакета отслеживается одним ограниченным чтением <code>get_project_agent_queue</code>. Оно возвращает счётчики состояний проекта, краткие задачи, блокировки, компактные результаты и подходящие следующие действия. По умолчанию видны только очередь, выполнение, ожидание ответа и результаты на проверке; <code>unresolved_only=false</code> нужен только для просмотра истории.

Для новой обычной задачи тот же путь сокращается до одного вызова: <code>create_task</code> с <code>run_with_agent=true</code> одновременно создаёт задачу и ставит её в очередь. Флаг не включается по умолчанию и используется только при явной просьбе пользователя выполнить работу, а не просто сохранить её.

## Карта возможностей

### Рабочая область и проекты

- Получение компактной сводки рабочей области или проекта.
- Просмотр, создание, переименование и чтение проектов.
- Обновление свободного Markdown-контекста.
- Просмотр и настройка структурированных источников проекта.
- Диагностика локального хранилища без изменений.

MCP не может самостоятельно открыть себе доступ к источнику. Новый источник или изменённый адрес остаётся закрытым, пока пользователь не включит доступ в desktop-приложении.

### Документы, правила и skills проекта

- <code>list_project_workspace_items</code> возвращает карточки доступных материалов: ID, тип, название, summary, версию, размер текста и число доступных прошлых версий. Markdown и тела истории по умолчанию отсутствуют. Страница содержит 20 элементов (`limit`: 1–100); пока `remaining` больше нуля, продолжайте через `next_cursor`. Cursor связан с ревизией контекста и `kind`: при их изменении начните список заново. Поле `content` отсутствует, а не обозначает пустой текст; `include_content=true` добавляет текущий Markdown. Просмотр списка не засчитывает чтение обязательного rule.
- <code>get_project_workspace_item</code> возвращает полный текущий Markdown и версию, а также `revision_count` и `history_included`. История по умолчанию исключена; `include_history=true` явно запрашивает доступные прошлые версии (каноническая история хранит до восьми). Выключенный Agent access блокирует чтение и исключает материал из списка; версии, сохранённые без Agent access, также не раскрываются. Эти проекции ничего не удаляют из канонической истории.
- <code>create_project_workspace_item</code> создаёт документ, правило или skill с безопасным повтором по <code>request_id</code>. При включённом Project Work Context новый rule или skill не может сам выдать себе <code>agent_access=true</code>: он создаётся скрытым, а человек включает Agent access в приложении после проверки. Документы можно создавать сразу доступными агенту, если у вызова уже есть право на мутацию проекта. Ответы мутаций возвращают текущее содержимое, но не тела прошлых версий; каноническая история сохраняется и доступна только через явное чтение истории, если Agent access это разрешает.
- Обновление всегда проходит через <code>preview_project_workspace_item_update</code>, а затем <code>apply_project_workspace_item_update</code> с неизменившимся preview-токеном и актуальной версией.
- Предыдущие версии сохраняются в ограниченной истории. Доступ агента к каждому материалу выключен, пока пользователь не разрешит его явно.

Память хранит факты и решения, правила — обязательные ограничения, skill — воспроизводимую процедуру. Внешняя папка skill остаётся ссылкой-источником; project-owned skill хранится и версионируется самим flood.md.

Миграция клиентов: для чтения Markdown из списка теперь нужны `include_content=true` и обход страниц либо точечное чтение материалов. Для истории одного материала явно передавайте `include_history=true`. Прежние поля ответа `item`, `created=false` и `request_id=null` сохранены. Изменения API требуют пересборки и перезапуска MCP: редактирование исходников не обновляет уже работающий сервер.

### Память проекта

- Чтение и поиск по ограниченному набору актуальных решений, ограничений и проверенных способов работы.
- Добавление подтверждённого факта с безопасным повтором запроса и необязательной ссылкой на исходную задачу.
- Закрепление небольшого числа фактов, которые всегда должны попадать в компактный рабочий контекст.
- Исправление формулировки с сохранением до десяти предыдущих версий или явная замена изменившегося решения без стирания истории.
- Удаление доступно только в отдельно включённом режиме необратимых MCP-действий; при изменении решения предпочтительнее замена.

Память проекта — не transcript и не вторая база знаний. В сводку проекта и рабочий контекст задачи попадают только актуальные записи: сначала закреплённые, затем недавние, в жёстком лимите. История замен доступна через <code>list_project_memory</code> только по явному запросу. Любое содержимое памяти остаётся недоверенными данными проекта, а не инструкцией или расширением полномочий агента.

### Задачи

- Просмотр, поиск, чтение, создание и изменение задач.
- Срочность, завершение, перенос между проектами и восстанавливаемая корзина.
- Получение задачи вместе с контекстом, необходимым для выполнения.
- Связанные задачи, подзадачи, блокировки и вычисляемая готовность к работе.
- Постановка задачи в локальную очередь, чтение состояния, ответ на реальный блокер и принятие результата без дополнительного действия в UI.
- Стабильные request ID для защиты от дублей и безопасных повторов.

Необратимое удаление по умолчанию выключено. Оно доступно только серверу, явно запущенному с <code>FLOOD_MCP_ALLOW_DESTRUCTIVE=1</code>.

### Telegram

- Проверка свежести синхронизации и частичных ошибок desktop-приложения.
- Единая хронологическая лента связанных чатов проекта.
- Постраничное чтение одного локально кешированного чата без выгрузки всей истории.
- Ограниченное окно вокруг выбранного сообщения и его прямой reply parent, если он доступен.
- Стабильный ID автора для различения участников с одинаковыми именами и признак сообщений подключённого владельца.
- Короткие проектные роли участников, например «CEO» или «Backend + DevOps». Роль — это контекст, а не полномочие.
- Входящие кандидаты, пропуск, восстановление и сохранение снимка источника задачи.
- Telegram-альбомы как одна реплика обсуждения.
- Явный запрос одного изображения; лимит 8 МБ, локальные пути наружу не передаются.
- Preview и применение пакетного плана с проверкой изменившихся сообщений, пересечений контекста и дублей.

Скользящий кеш хранит до 100 сообщений на чат, а один MCP-ответ возвращает не больше 50. Окно контекста по умолчанию включает три сообщения до и после выбранного и расширяется только в документированных пределах.

Роли намеренно сделаны лёгкими: они хранятся вместе с проектом, редактируются в настройках Telegram-чатов и могут быть предложены через MCP. flood.md не создаёт отдельный справочник сотрудников и не требует описывать структуру команды.

### Источники проекта и GitHub

В разрешённой локальной папке или репозитории агент может получить ограниченное дерево, выполнить текстовый поиск и прочитать выбранный UTF-8 файл. Доступ не выходит за заданный корень и пропускает генерируемые каталоги и похожие на секреты файлы.

Для разрешённой локальной Git-копии контекст задачи дополнительно показывает ветку, HEAD, изменённые пути, компактный безопасный diff, до пяти совпавших недавних коммитов и до двадцати совпавших отметок в коде. Поиск просматривает не больше шестнадцати коммитов и 400 отслеживаемых файлов. Один ответ ограничен четырьмя настроенными источниками, 100 изменёнными путями на источник, восемью файлами diff и 40 000 символами diff. Если источником назначена вложенная папка, это не открывает агенту остальную часть репозитория.

GitHub App работает только на чтение. Агент может получить ограниченные метаданные репозитория, README, открытые issues и pull requests, список файлов, поиск и выбранный файл. Доступ одновременно ограничен установкой GitHub App и репозиториями, связанными с проектом flood.md.

Figma и сайты пока остаются ссылками для внешнего коннектора: flood.md самостоятельно их не загружает.

## Модель безопасности

- Задачи, сообщения и файлы репозитория считаются недоверенными данными, а не разрешением выполнять команды или внешние действия.
- Передача Telegram-текста и изображений фоновой модели выключена, пока пользователь явно не включит её в desktop-настройках.
- Создание задачи само по себе не разрешает выполнять её или отправлять сообщение в Telegram; выполнение начинается только отдельным явным вызовом <code>queue_task_for_agent</code> по запросу пользователя.
- Ограниченные выборки не выгружают весь чат или репозиторий в контекст модели.
- Планы Telegram-задач проходят preview и валидацию перед записью.
- Изменившиеся сообщения или контекст проекта делают старый токен плана недействительным до любых изменений.
- Стабильные request ID защищают повторные вызовы от дублей.
- Desktop и MCP используют общие правила проверки, блокировки, конфликтов и журнал действий без текста задач и сообщений.
- Данные авторизации Telegram и GitHub не сохраняются в Markdown или резервных копиях.

## Диагностика

Экран **Настройки → MCP и AI** показывает совместимость версий, здоровье хранилища, ограниченный журнал метаданных и изолированную самопроверку.

~~~powershell
flood-mcp.exe --version
flood-mcp.exe --manifest
flood-mcp.exe --self-check
~~~

`--manifest` возвращает версию сервера, согласуемую версию протокола, число tools и стабильную семантическую ревизию их полного каталога. Та же ревизия доступна через `get_runtime_info` и показана в настройках. Протокольная проверка запускает чистую stdio-сессию, проходит `initialize` → `initialized` → все страницы `tools/list` и требует точного совпадения числа tools и SHA-256 fingerprint с runtime и manifest. Если бинарник и уже подключённая сессия сообщают разные ревизии или в ответе сессии ревизии ещё нет, перезапустите MCP-клиент либо откройте новую сессию: каталог статического stdio-сервера фиксируется при запуске процесса, поэтому `listChanged` для него не объявляется.

Самопроверка использует временное изолированное хранилище и не меняет проекты пользователя.
