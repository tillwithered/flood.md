# Component contracts

Status: normative specification, 20 September 2026. These contracts define required behavior for new or changed UI within the requested scope; they are not a component inventory, an implementation claim, or evidence that the current desktop build passes them. Existing Svelte markup may satisfy only part of a contract. Read the [entry contract](README.md), [foundations](foundations.md), [flows](flows.md), and [verification gates](verification.md) together.

The selected direction is [Quiet Workbench](quiet-workbench.md), **utilitarian minimalism with sparse original flood identity**. Project-owned composition, accessibility, ownership, and trust rules remain the starting point. A new shared composition must be proved on the three anchor surfaces in Tauri before broad propagation. A local correction needs verification of its affected flow; a specification needs document validation. This document does not authorize new product features.

## How an agent uses this matrix

1. Select the component family by user intent, not by resemblance to a screenshot. Record its ID in the change plan.
2. Find the existing implementation before creating a new Svelte component. These are contracts for shared behavior; this document does not require a file for every row.
3. Apply the common requirements below and the relevant row. Reuse existing CSS token names where sound; `--line-strong` and `--focus-ring` exist in the shared runtime source. [Foundations](foundations.md) owns values, aliases, and migration status.
4. Name unsupported states as migration work. Do not hide missing behavior with a visual mock, a no-op control, or an unsupported promise such as “Restored”.
5. Verify the complete affected flow, not only the component in isolation. Record implementation and verification status separately.

## Common requirements

| Concern | Required contract |
| --- | --- |
| Semantics | Prefer native `button`, `a`, `input`, `textarea`, `label`, `fieldset`, `legend`, and `dialog` semantics. A themed control still needs an accessible name, role, value, and state. Use ARIA only to complete the required pattern; never assign `role="button"` to a container holding other buttons. |
| Keyboard | DOM order follows reading order. Enter activates links; Enter/Space activate buttons; Space toggles checkboxes. Only real composite widgets use arrow-key navigation. Escape dismisses the topmost dismissible layer without discarding dirty content. Do not override editor, IME, or platform shortcuts. |
| Focus | Every interactive target has a visible neutral focus indicator, never clipped or hidden by a sticky header; `--focus-ring` owns its color. Focus and selection remain distinguishable. Opening a layer moves focus deliberately; closing it returns to the invoker or its nearest surviving equivalent. Passive refresh does not steal focus. |
| Targets | At least 24 × 24 CSS px; aim for 32–40 px control height on desktop. Icon size is independent from hit area. Adjacent targets do not overlap. Do not shrink text or targets to fit a narrow window. |
| State | Specify resting, hover, pressed, focus-visible, disabled, selected/expanded when meaningful, and busy/error for async actions. Disabled is not a loading state. Busy state preserves the action label and geometry, exposes a truthful accessible status, and prevents duplicate submissions. |
| Color | Controls use monochrome roles in all interaction states. Semantic color belongs to urgency, status, a meaningful error, a destructive confirmation, or live operation progress. Connector logo color does not tint the control. Text or shape carries meaning when color disappears. |
| Type and content | Golos Text semantic roles from foundations; visible text never below 12 px. Required labels and actions use body roles, not faint captions. A visible control label has at most two words; move object identity and consequence to nearby copy while keeping a complete accessible name. Russian examples below are product copy, while these instructions are English. Missing optional metadata is omitted, not rendered as `undefined`, a dummy date, or an unexplained dash. |
| Shape and spacing | Parent layout owns outer gaps. The target distinguishes navigation rows, compact data rows with actions, and independent action rows; see the classification below. Independent action rows retain persistent 8–10 px rounded geometry, 8–12 px peer gaps, and no permanent separators between them. Grouped settings/data may use internal separators. Nested parallel contours follow `inner = max(0, outer − inset)`. Every rounded UI contour consumes shared corner smoothing when supported, with `border-radius` as the complete fallback; true circles and source artwork stay round/native. |
| Long content | Use `min-width: 0`, wrapping, and responsive stacks. Truncate only index summaries whose complete content has an accessible destination. Do not truncate the only distinguishing part of duplicate identities, an error recovery action, permission scope, or a confirmation consequence. Tooltips are not the only path to the full value. |
| Contrast and forced colors | Meet 4.5:1 for ordinary text and 3:1 for necessary boundaries, indicators, and focus. A filled, persistently labeled field may use the low-emphasis `--line` resting boundary; use `--line-strong` when the boundary itself is necessary to identify a control or state. In `forced-colors: active`, use system colors for surfaces, text, selected state, and focus; preserve outlines/borders and text alternatives when shadows, gradients, or blobs vanish. Do not disable forced-color adjustment globally. |
| Scroll and motion | One primary scroll container per working surface, with deliberate nested scrolling only for overlays, code, or long lists. Reserve scrollbar space; ordinary scrollbars are neutral. Horizontally scrolling tab bars have no visible scrollbar but must reveal focused/selected items. Respect reduced motion; busy status remains understandable when static. |
| Feedback | Inline validation stays associated with its field via `aria-describedby` and `aria-invalid`. Passive progress uses a polite status region. Blocking failures may use an alert once, without repeating on each render. Essential recovery never lives only in a transient toast. |

The canonical restriction on visually prominent native select menus concerns **appearance and interaction quality**, not a ban on native HTML semantics. A custom select must implement a complete accessible select-only combobox/listbox pattern. If that cannot be delivered and tested, use an accessible established implementation or explicitly defer the migration; do not ship a visually themed inaccessible substitute.

### Row classification

This narrowing amendment is part of the user-selected Quiet Workbench direction. It applies to the current slice; production acceptance and broad propagation still require the anchor gate.

| Row category | Target treatment | Examples |
| --- | --- | --- |
| Navigation row | Compact item within a navigation list; neutral hover/current/focus treatment. No requirement for a separately filled floating card or 8–12 px gap around every item. | C09 project navigation; no sidebar task tree. |
| Data row with separate actions | Compact, readable collection row; completion and open actions remain separate. Use a coherent list surface; optional structural separators belong to the collection. Do not manufacture a card around each task. | C10 task index, noninteractive C16 history details. |
| Independent action row | A standalone object-opening control with persistent rounded shape and 8–12 px peer gap. It may use a neutral surface; its hover does not become square or extend beyond the target. | C14 artifact opener, C20 full-row disclosure. |

The configured desktop minimum is **760 × 560** in [`src-tauri/tauri.conf.json`](../../src-tauri/tauri.conf.json). Treat that as the current narrow-window baseline, alongside 1280 × 800 and 1024 × 768 reference views. Text zoom is an additional test; changing the native minimum requires a separate implementation decision.
